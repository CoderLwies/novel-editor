# 复盘：小说导入分析功能（已移除）

> 结论先行：这条路在当前条件下**不成立**，功能已从代码中移除，保留 git 历史
> （`feat/novel-reference` 分支，2026-10 前后）以便日后重新设计时查阅。

## 当时要解决什么

网文作者写自己的书时想借鉴别人：「这本书怎么分卷的」「这一章在结构上干了什么」
「金手指怎么设计的」「爽点密度多少」。想法是导入他人小说 → AI 拆解 → 拆成
可迁移的方法 → 写作时随时调出来对照。

## 为什么失败

### 一、成本不可控（致命）

实测一部 985 章 / 347 万字的小说：

| 项目 | 数值 |
|---|---|
| 批次 | 293 批（4 章/批） |
| 实际账单 | **¥39.44** |
| 界面预估 | ¥12.36（**低估 3.2 倍**） |

低估的三个来源：

1. **输出量假设错了 7.7 倍**。最初按「每批输出 800 token」估，实测是 6183
   ——每个情节拍都带 title/summary/signal/cost/characters 五个字段，长篇一拍的
   文字量远超「每批几个标签」。
2. **重试消耗不记账**。`runOne` 只在成功时返回结果，失败尝试烧掉的 token
   完全隐形。用户的账单和界面对不上，预算控制也就失去意义。
3. **峰谷定价没算**。DeepSeek 2026-08-17 起实行峰谷分时定价，高峰时段
   （9-12 / 14-18）直接翻倍。

结论：**「花几十块拆一本书」这个前提，用户不会接受第二次。**

### 二、质量不可信（致命）

- **章节切分误判 16%**。网文里「第一节课」「第二节晚自习」是极其常见的正文
  用语，被「第X节」当成章节单位切了出去。一部 985 章的书里误判 186 处。
  这直接污染了全部三个分析阶段的输入。
- **产物看不见**。293 批全部跑完、原始数据都在磁盘上，但最后一步「组织叙事线」
  那一次调用失败 → `plot.json` 一行没写 → 用户花 ¥39 什么都看不到。
  （根因：beats 和 arcs 没有分阶段落盘。）
- **重跑比第一次还贵**。修完误判后章节数变了，批次划分随之改变，旧缓存
  作废，只能从头再花一遍。

### 三、投入产出不成立

即使上述问题都修好，得到的也只是**一份你读不完的 Markdown 报告**。
真正有用的形态是「写到某一章时，提示我这里该是什么功能」——但那需要
把参考书的情节特征抽象得足够准，而这恰恰是最难、最容易出错的一步。

## 踩过的坑（值得记住的教训）

### 1. 单测全绿 ≠ 功能可用

单测用的 fixture **全来自「已经跑过一遍」的目录**，所以下面这些状态
从来没被测到：

- 新书第一次跑分析（`analysis/raw` 还不存在）→ 直接 ENOENT 崩溃，
  **任何新书第一次跑都会中招**
- 拆章规则变更后的存量数据 → 缓存静默失效
- 骨架阶段失败 → 全部成果丢失

**测试数据的「形态」和「内容」一样重要。** 以后要专门覆盖：
空目录、缺失文件、首次运行、规则变更后的旧数据。

### 2. 成本预估要有实测校准，不能靠推理

我按「每批 800 token 输出」推理，实测 6183，差 7.7 倍。
**任何「每单位产出多少」的假设，都要用真实跑一遍的数据校准。**

### 3. 分阶段落盘：每一步的产出都要独立可见

最后一步失败就让前面全部白费，这个设计是错的。正确做法：
**中间产物先落盘，后续步骤失败不回收已完成的部分。**

### 4. 让「钱花在哪」可见

用户看到 ¥39.44 而界面显示 ¥12.36，信任就没了。
记账必须包含失败尝试、重试、以及所有实际计费项。

## 什么被保留了

移除的是「导入他人小说 + AI 拆解」这条链路，这些与参考库无关、
各自独立成立，全部保留：

- **正文落盘**：章节正文写 `chapters/*.md`，localStorage 只存元数据。
  实测 300 章 / 105 万字的状态体积从 2.27MB 降到 0.26MB。
  （顺带发现：书架的「导入 TXT/MD」也吃这条路径。）
- **GBK 编码探测**：国内网文 txt 大量是 GBK，Node/Electron 内置
  `TextDecoder` 原生支持，零依赖。
- **拆章容错**：序章 / 楔子 / 番外 / 后记 / 「正文 第X章」/ `Chapter N` /
  Markdown 标题分卷。

## 如果要重新做，先回答这四个问题

1. **用户愿意为一次分析付多少钱？** 答案决定「能否用 AI 跑全书」。
   如果答案是「零」或「几毛」，那就不该用 AI 逐章分析。
2. **要解决的到底是哪个决策？** 「这本书怎么分卷」和「我现在这章该写什么」
   是两个完全不同的问题，需要的抽象层级和成本量级差一个数量级。
3. **为什么必须是逐章 AI 分析？** 备选：只分析开头 30 章（黄金三章）、
   只做全书统计（本地，零成本）、让用户手动标注参考段落再归纳。
4. **失败时用户损失什么？** 现在是 ¥39 打了水漂。下一个设计的第一条
   验收标准应该是：**任何环节失败，已付费的成果全部可见。**
